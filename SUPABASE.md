## Database migration and existing data

First inspect the project's existing schema. Apply `supabase/migrations/20261013194907_royal_t_backend.sql` through the Supabase SQL editor or your linked Supabase CLI migration workflow after checking existing objects. It adds namespaced `royalt_*` tables and does not drop existing tables, truncate data or replace old models. Its timestamp was generated by the Supabase CLI.

Tables cover customers and billing, courier partners, shipments, tracking events, enquiries, document metadata, payments, staff profiles, activity and sync runs. Indexes, foreign keys, positive numeric constraints, reference uniqueness and event uniqueness are included. Every business table has RLS. Public users have no direct business-table access. Active staff authorization is checked against profiles and the current Auth session; user-editable metadata never grants roles. Server routes validate users before privileged document/intake/invitation operations.

The existing record fields map to shipment/customer/enquiry columns; `legacy_data` retains older metadata. The contact, quote, pickup, booking and assistant issue details are preserved in enquiry payloads. Quote estimates are descriptive request data, never trusted billing amounts. Retries keep one reference using an idempotency UUID. A quote/enquiry can be converted to a shipment request without losing the customer or original reference. This creates an internal request, not a DHL/UPS booking.

To import a legacy `data/internal-store.json`, run `node scripts/import-legacy.mjs` for a count-only dry run. Back up the private source first. After configuring server variables locally, run `node --env-file=.env scripts/import-legacy.mjs --apply`. The source remains unchanged; idempotency IDs make retries safe. Local staff passwords and sessions are not migrated to Supabase Auth. If the old deployment used `royalt_store` in PostgreSQL, export its `data` value into a private JSON file and set `INTERNAL_STORE_PATH` to that file for this importer. Do not commit exports or keys. Low-entropy old references are retained privately and replaced by new public references.

## Invite-only staff access

Disable public signups and anonymous sign-ins in Supabase Auth. Set the Auth Site URL to `APP_URL` and allow the exact `/internal` invitation redirect. Set a short access-token lifetime appropriate for the staff workspace. Configure SMTP for staff invitations if the project's default mail restrictions prevent delivery.

Create the first administrator through the Supabase Auth dashboard with a private password. Add its Auth user UUID to `royalt_staff_profiles` as `role='admin'`, with the same email and `active=true`; this is a one-time administrator action. There is no public setup or registration endpoint. Administrators then use Staff access → Invite a staff member. Staff use email/password login. Session/refresh tokens stay in HttpOnly, SameSite cookies, with Secure cookies on Vercel. Logout revokes the local Auth session, and RLS checks session existence as well as active staff membership.

For the invitation email template, use a link of the form `{{ .SiteURL }}/internal?token_hash={{ .TokenHash }}&type=invite`. The existing internal page exchanges the one-time invite token server-side and asks for a password of 12 or more characters. It does not consume browser-fragment tokens or expose staff JWTs in browser storage. Remove old invite links before sharing screenshots. Role changes or deactivation can be administered in `royalt_staff_profiles` by the Supabase project administrator; staff cannot edit their own authorization profile.

The dashboard includes paginated/searchable shipments, pending/in-transit/delivered/exception counts, recent enquiries, enquiry status/notes, customers and shipment history, package/sender/receiver editing, courier assignment, external tracking numbers, manual confirmed tracking events, document uploads and charges/payments/outstanding balances. Shipment edits use optimistic concurrency and an atomic activity update. Payment entries are bookkeeping records; they do not charge a card or generate a GST invoice.

## Private shipping documents

The migration creates a private `royalt-documents` bucket with a 2 MB PDF limit. Uploads pass through the authenticated server for size, MIME and PDF-signature checks. No public bucket access or public upload policy is granted. Staff download links expire after 60 seconds. Reopen the panel to refresh links. Document metadata links each object to its shipment and uploader. A failed metadata save attempts to remove its newly uploaded object. Review and remove orphaned objects if cleanup ever fails.

Keep only essential PDFs, avoid duplicates and monitor Storage usage. Choose an approved retention period for shipping documents and customer information; no destructive automatic retention has been applied to existing data.

## Tracking and hourly scheduler

The public `/tracking` page calls `/api/tracking?id=REFERENCE`. It reads cached database rows and never contacts a courier during a customer visit. It returns only the random internal reference, courier name, status, timeline, latest city/location, estimated delivery and last sync time. It excludes contact details, addresses, payment amounts and operational notes. Rate limits apply to lookups, logins and submissions, with salted IP digests stored privately. The forms also include a honeypot; these controls are baseline spam protection, not a claim that all automated abuse is prevented.

Set `DHL_TRACKING_API_KEY` for the documented DHL Unified Tracking API. Set `UPS_CLIENT_ID` and `UPS_CLIENT_SECRET` for UPS OAuth; `UPS_ENVIRONMENT=sandbox` is the default. Change it to `production` only for an approved live tracking account. No carrier shipping/purchase endpoints are called. Booking and label methods deliberately reject until an approved shipping adapter exists; staff can upload labels from their carrier tool. Mock adapters are injected only into development tests and never selected through a production flag.

In your cron-job.org account, create a free job for:

- URL: `https://website-plum-tau-44.vercel.app/api/cron/tracking` (use the same existing production host if it changes).
- Method: POST.
- Header: `Authorization: Bearer YOUR_CRON_SECRET`.
- Schedule: hourly, timeout 60 seconds; never put the secret in the URL.

The endpoint uses a database lock to stop overlapping runs, processes at most 8 due active shipments within its time budget, normalizes events, deduplicates events, backs off failed requests and stops polling delivered/cancelled shipments. It keeps redacted failure summaries. DHL calls are spaced at least five seconds apart. With more than 8 due shipments, the oldest due rows are handled first on subsequent runs; hourly scheduling does not promise an hourly refresh of every shipment when a batch exceeds the time/provider quota. Request a suitable DHL production quota before increasing throughput: its documented initial allowance is 250 calls/day and one call per five seconds. Confirm the courier agreement and required attribution/retention before enabling live tracking; the public DHL display includes the required attribution. DHL's documented default deletion requirement for tracking data after delivery must be incorporated into your approved retention procedure.

This scheduler is not yet connected to an external account. Hourly activity does not guarantee Supabase Free avoids inactivity pauses. Monitor project health and storage/database quotas. This design does not require a VPS, Redis, a paid queue or a second production database.
